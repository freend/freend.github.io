새 서비스를 운영 환경에 올릴 때 가장 먼저 필요한 건 저장소 탐색이 아니다. 어떤 서비스를 어느 환경에 배포할지 정하는 일이다.

저장소 안에는 애플리케이션 코드뿐 아니라 테스트용 설정, 예제 매니페스트, 오래된 배포 파일도 함께 있을 수 있다. 파일 이름만으로 무엇이 현재 운영 대상인지 판단하기 어렵다. 그 결정은 코드를 읽는 것만으로 알 수 있는 정보가 아니라, 서비스를 운영하는 사람이 가진 의도이기 때문이다.

그래서 배포 준비의 시작을 간단하게 정했다.

> “이 서비스를 운영 환경에 배포할 거야.”

이 말을 들으면 AI가 저장소 전체를 뒤져 배포 대상을 추측하는 대신, 해당 배포에 필요한 값을 확인한다.

## 먼저 배포 정보를 확정한다

Kubernetes 배포와 CI/CD 구성을 준비하려면 적어도 다음 정보가 필요하다.

- 서비스 이름과 Terraform 모듈 이름
- Git 저장소 주소와 브랜치
- Kubernetes 네임스페이스
- Deployment와 Service 이름
- 서비스 도메인과 매니페스트 경로
- 빌드 설정 파일의 위치

api-log-exporter 사례에서는 운영 대상이 정해진 뒤 저장소와 main 브랜치, monitoring 네임스페이스, Deployment와 Service 이름 등을 확인했다. 값이 빠졌거나 서로 맞지 않으면 임의로 채우지 않고 사용자에게 다시 물었다. 이름 규칙에 맞는 기본값을 제안할 수는 있지만, 기본값과 요청이 다를 때는 어떤 값을 쓸지 확인한 다음 진행한다.

이 확인 과정은 대화를 길게 만들기 위한 절차가 아니다. 뒤 단계의 Kubernetes 설정과 CI/CD 요청이 같은 서비스, 같은 네임스페이스를 가리키도록 입력을 한 번 정리하는 단계다.

## 확정된 값으로 매니페스트를 준비한다

입력이 정해지면 AI는 기존 Kubernetes 운영 기준에 맞춰 ConfigMap, Deployment, Service, HTTPRoute 같은 매니페스트를 준비한다. 파일마다 대상 네임스페이스와 리소스 이름을 명확히 하고, Deployment가 올바른 ConfigMap과 Service를 참조하는지도 확인한다.

설정 파일과 기밀 정보는 애플리케이션 코드처럼 무심코 배포하지 않도록 별도 취급한다. ConfigMap과 Secret은 사용자가 정확히 지정한 경우에만 배포 목록에 넣고, Secret 값은 출력이나 작업 기록에 남기지 않는다.

실제 적용 전에는 배포할 파일과 각 파일의 리소스 종류, 이름, 네임스페이스를 목록으로 만든다. 해당 파일만 server-side dry-run과 diff로 확인하고, 디렉터리 전체를 대상으로 한 적용은 피한다. 매니페스트가 많아져도 검토 대상과 실제 변경 범위를 사람이 확인할 수 있도록 하기 위해서다.

여기서 AI의 역할은 배포 의도를 새로 결정하는 게 아니다. 사람이 정한 대상과 확인된 입력을 일관된 설정으로 옮기고, 빠진 연결이나 검증 단계를 찾아 보여주는 것이다. 실제 클러스터 변경은 사용자가 배포 대상과 실행을 명시한 뒤에 진행한다.

## 다음 단계에 넘길 수 있는 요청 정보

Kubernetes 쪽 설정이 준비되면 확정된 서비스 이름, 저장소와 브랜치, 네임스페이스, Deployment와 Service, 도메인, 빌드 파일 정보를 하나의 요청으로 정리한다. 이 요청은 다음 단계인 ECR과 CI/CD 인프라 구성에 그대로 전달된다.

사람이 “무엇을 배포할지” 결정하고 필요한 입력을 제공하면, AI는 같은 질문과 준비 작업을 매번 처음부터 반복하지 않아도 된다. 다음 글에서는 이 확인된 정보가 Terraform과 CI/CD 구성 요청으로 이어지는 흐름을 살펴본다.
